# slab-bot DB 확장 설계 (레이어 · 기준 · 백로그)

> **목적** — slab-bot 답변 품질을 위해 DB를 확장하되, "무작정 붙이기"가 아니라 **레이어와 기준**을 두고
> 어떤 데이터를 어떤 순서로 붙일지 체계화한다. 이 문서는 확장 백로그의 기준선(baseline)이다.
> 관련: [`slab-event-model.md`](./slab-event-model.md)(이벤트 카탈로그), 등기부 추출·전문가 매칭·Jandi 적재 트랙.

## 0. 인터뷰로 확정된 전제 (2026-07-23)

| 축 | 결정 | 함의 |
|---|---|---|
| **병목** | 커버리지 부족 + 근거/출처 부족 | "모르는 게 많고, 아는 것도 왜 그런지 못 보여준다" |
| **확장 축** | 회사·포트폴리오 심화 + 이벤트·타임라인 | 재무/인력/제품 심화 + 시계열 |
| **회사 범위** | **포트폴리오 337개사 심화** (딜 유니버스 확장 X) | 사업자번호 아는 회사만 → 신규 발굴·중복문제 없음 |
| **접근 방식** | 하이브리드 (정형 도구 + RAG) | 정형값은 tool, 비정형은 임베딩 검색 |
| **소스 신뢰** | 자동추출 우선 → **단, 외부 API는 무용** | 비상장사라 DART·뉴스·기업정보DB 공시 없음 |
| **실제 원천** | **내부 비정형 문서** (메일·드라이브·PDF·대화) | "자동추출"의 대상 = 외부 API가 아니라 **내부 문서** |
| **타임라인** | 분기 diff 파생 + 문서 첨부 | `quarterlyupdate` 시계열을 척추로 이벤트 파생 |
| **소스 우선순위** | ① slab 기존 첨부 → ② 구글드라이브 → ③ 이메일 → ④ 메신저·미팅 | 비용↑·정리부담↑ 순 |
| **추출 항목** | 재무·런웨이 / 라운드·투자자 / 인력·조직·인물 / 제품·KPI·리스크 (전 파트) | 사용자를 **전 직원**으로 확대 예정 → 모든 파트 대응 |
| **권한** | 확장(민감) 데이터는 **심사역·내부만** | 아래 §1-4 티어 긴장 참조 |

> **⚠️ 짚어둔 긴장** — "전 직원 확대"(사용자) ↔ "심사역·내부만"(권한)은 충돌한다.
> 해법: **데이터 티어**. 회사 기본·제품 = 전 직원, 민감(메일·재무 상세·라운드 조건) = 심사역-only.
> → 모든 확장 테이블에 `visibility` 축을 필수로 둔다(§1-4).

## 1. 설계 원칙 (hard rules) — 확장의 헌법

붙이는 모든 데이터는 아래 5원칙을 통과해야 한다.

1. **출처 필수 (Provenance)** — 병목이 "근거 부족"이므로 모든 확장 테이블은
   `source`(원천 종류) · `source_ref`(문서/행 ID·URL) · `extracted_at`(신선도) · `confidence`(추출 신뢰도)를 **필수 컬럼**으로 갖는다.
   도구 응답·RAG 결과에 이 출처를 실어 보내 봇이 "○○사 2025-Q2 IR메일 기준"처럼 근거를 제시한다.
2. **원천 우선 자동추출** — 내부 문서에서 LLM/파서로 추출하는 것이 기본. **수기 입력은 자동으로 못 얻는 것에만** 허용.
3. **계산값 저장 금지** — `valuation`·`share ratio`·이벤트 파생값은 저장하지 않고 계산·파생한다(이벤트 모델 §4 교훈). 원천만 정확하면 정합.
4. **접근 티어 (Access-tier)** — 모든 확장 행/필드에 `visibility` = `all_staff` | `analyst_only`. RLS로 강제. (전 직원 확대 대비)
5. **원본 불변 (Immutable Raw)** — 원본 문서·스냅샷은 그대로 보존하고, 추출은 그 위 레이어에서 수행. 재추출·감사 가능하게.

## 2. 레이어 모델 — 데이터가 봇 답변에 닿기까지

```
┌─ L0 원천(Raw) ────────── 원본 문서 불변 보관
│   slab 첨부 PDF · 드라이브 파일 · 메일 · 메신저 로그
│        │ (파싱·LLM 추출)
├─ L1 추출(Extract) ────── 문서 → 구조화 필드 + confidence + source_ref
│   재무·라운드·인력·제품 값 (문서 단위)
│        │ (정규화·정합)
├─ L2 정규(Canonical) ──── 회사별 최신 정합 뷰 + 엔티티(people 등)
│   기존 company·quarterlyupdate와 병합
│        │ (분기 diff)
├─ L3 파생(Derive) ─────── 스냅샷 diff → company_events(타임라인)
│        │
└─ L4 접근(Access) ─────── 정형 도구(쿼리) + RAG(임베딩)
     ↑ 전 레이어 가로지름: Provenance(출처) · Access-tier(권한) · Freshness(신선도)
```

- **L0**는 새 테이블 `documents`(회사·날짜·출처·blob참조) 하나로 통일 — 소스가 뭐든(PDF/드라이브/메일/메신저) 같은 스키마로.
- **L1** `document_extractions` — 문서에서 뽑은 항목별 값 + `confidence` + 원문 스니펫.
- **L3** `company_events` — `quarterlyupdate` 연속 행 diff로 파생(라운드/인력/런웨이/밸류 변화) + L1 추출 이벤트.
- **L4** — 정형은 기존 tool 패턴 확장, 비정형은 `documents`/`document_extractions`에 임베딩.

## 3. 확장 기준 (판정 체크리스트) — "이 데이터 붙일까?"

새 데이터/컬럼/소스 후보는 아래를 통과해야 백로그 승격.

> 이 체크리스트는 **통과/탈락 게이트**라 순서를 만들지 못한다.
> **우선순위**는 **§7 우선순위 평가**의 가중점수 모델로 매긴다.

| 기준 | 질문 | 탈락 예 |
|---|---|---|
| **수요** | 실제로 물어보는데 못 답하는 gap인가? | 아무도 안 묻는 필드 |
| **중복** | 이미 slab/기존 테이블에 있나? | company에 이미 있는 값 재적재 |
| **신선도** | 자동 갱신되나? stale 안 되나? | KVIC처럼 2023에서 멈춘 데이터(연동 철회) |
| **신뢰** | 출처 검증·근거 제시가 되나? | 출처 불명 스크랩 |
| **유지비** | 수기 부담이 지속 가능한가? | 매주 손입력해야 유지되는 표 |
| **권한** | visibility 티어가 정해지나? | 민감도 판단 불가한 데이터 |

## 4. 확장 백로그 (우선순위 = 소스순 × 가성비)

> ⚠️ **아래 Phase 0~4는 "소스 확보 난이도순" 초안이다.** 2026-07-27 질의 로그·필드 채움률 실측 결과
> **소스 난이도와 실제 수요가 역상관**임이 확인되어(Phase 2~4가 하위권으로 강등),
> 착수 순서는 **§7**의 실측 순위를 따른다.
> Phase 0·1은 완료됐으므로 아래는 그 기록으로 남긴다.

### Phase 0 — 타임라인 척추 (데이터 이미 있음, 최고 가성비, 외부의존 0) ✅ 완료(2026-07-26)

`quarterlyupdate` 2,205행은 이미 회사별 분기 시계열이다. **추가 수집 없이** diff만으로 이벤트 파생.

- **산출**: `company_events`(company_id, event_date, type, before/after, source_ref=quarterlyupdate row)
- **파생 규칙 예**: funding series 신규 등장 → `ROUND`, 직원수 급변 → `HEADCOUNT`, 런웨이 급감 → `RUNWAY_ALERT`, latest share price 변동 → `VALUATION`

## 5. 스키마 스케치 (초안 — 확정 아님)

```sql
-- L0: 모든 소스 공통 원본
documents(
  id, company_id, source,            -- 'slab_attach'|'drive'|'mail'|'chat'
  source_ref, title, doc_date,       -- 원문 식별·날짜
  storage_ref, ingested_at,
  visibility                         -- 'all_staff'|'analyst_only'
)

-- L1: 문서에서 뽑은 구조화 값
document_extractions(
  id, document_id, company_id,
  category,                          -- 'financial'|'round'|'people'|'product'|'risk'
  field, value_num, value_text, unit, as_of_date,
  confidence, snippet,               -- 근거 스니펫
  visibility
)

-- L3: 파생 타임라인
company_events(
  id, company_id, event_date, type,  -- 'ROUND'|'HEADCOUNT'|'RUNWAY'|'VALUATION'|...
  before_json, after_json,
  source, source_ref, derived_at
)

-- (선택) 사람 엔티티 — 인력·핵심인물 축
people( id, company_id, name, role, source_ref, visibility )
```

> 임베딩은 `documents`/`document_extractions`에 pgvector 컬럼 또는 별도 테이블. RAG 대상.

#### 축 설계 시 지킨 원칙

- **축은 적을수록 방어 가능하다.** 상관된 축은 같은 항목을 중복 가점한다(H 오답위험 + X 실행비용 → `Q`로 통합). 9축을 상한으로 둔다.
- **민감도 검증을 거친다.** 배점을 0~8로 쓸어 순위가 안 바뀌는 축은 논쟁하지 않는다.

### 7.3 민감도 검증 결과

각 축의 배점을 0~8로 스윕하고 극단 시나리오 9종을 돌렸다(`scripts/priority-score.mjs --sensitivity`).
인접 근사동점(91점 vs 90점)의 자리바꿈은 의미가 없으므로 **"상위5 집합(구성)"** 과 **"상위3 순서"** 를 나눠 본다.
전자가 바뀌면 *착수 대상*이 달라지고, 후자가 바뀌면 *착수 순번*만 달라진다.

| 발견 | 함의 |
|---|---|
| **상위5 집합은 9개 축 전 구간에서 불변** (유일 예외: `T`를 7 이상으로 올릴 때) | **착수 대상 5개는 배점과 무관하게 확정.** 어떤 걸 할지는 논쟁 대상이 아니다 |
| **극단 시나리오 9종 중 8종에서 Exit·법인상태가 모두 상위3**, 6종에서 상위2 독점 | 1·2위 확정. 다투는 건 둘의 순서뿐 |
| **D(수요빈도)는 상위5 집합을 전혀 못 바꾼다** (상위3 순서만 `w≤2`에서 변동) | 수요 높은 항목이 다른 축에서도 높아 상관이 걸림. 부수효과로 **n=19 표본 문제가 결론을 위협하지 않는다** |
| `L(파급범위) ≥ 3`이면 법인상태가 1위 | 1·2위 순서에 가장 민감한 축 |
| **U는 상위5 집합을 못 바꾸고, 상위3 순서만 `w≥2`에서 흔든다** | §7.5 매핑을 필드 단위로 자르자 상위권이 전부 `all_staff` 친화가 되어 U가 판을 못 흔듦 → **U=1(절충)로 확정** |
| `G(실패갭)=0`, `A(갱신자동화)=8`에서만 해외사업이 상위3에 진입 | 그 외에는 상위3 구성원이 고정 |

> **실무 함의** — 상위 5개는 집합이 고정이고 전부 비용이 낮다(개방 1·추가추출 1·도구화 2·신규 1).
> 순서 논쟁의 실익이 작으므로 **순차가 아니라 병렬 착수**가 가능하다.

### 7.4 접근 양식 트랙 — 정형 / 하이브리드 / 비정형

정형·비정형은 **점수 축이 아니라 트랙**이다. ① `T`가 이미 정형성을 재고 있어 이중계상이고 ② 좋고 나쁨이 아니라 어느 파이프라인으로 갈지의 문제이며 ③ 축의 의미가 트랙마다 다르다.

| 양식 | 정의 | 접근 | 판정 질문 |
|---|---|---|---|
| **정형** | 필터·집계·비교가 성립해야 하는 값 | tool | "몇 개? 어느 회사? 얼마?" |
| **하이브리드** | 문서에서 핵심 수치만 정형 추출 + 원문 보존 | tool + RAG | **재무제표가 이미 이 패턴** |
| **비정형** | 서술·문맥 자체가 값 | RAG | "왜? 어떻게? 무슨 맥락?" |

**비정형 트랙에서만 축을 교체한다** (배점 총합 유지 — 점수 인플레 방지):
- `T 추출결정성` → **`Rt 검색가능성`** (청킹 단위가 자연스러운가, 질문 어휘와 문서 어휘가 맞는가)
- `Cp 코퍼스 적정성`은 게이트로 처리 (§7.2)
- **`R` 감점 폭 확대** ← 아래 충돌 때문

> ### ⚠️ 티어 매핑표와 RAG의 구조적 충돌
> §7.5의 티어는 **필드 단위**로 잘랐는데, **RAG 청크는 필드 경계를 지키지 않는다.**
> IR덱 한 페이지에 제품 설명(`all_staff`)과 밸류에이션(`analyst_only`)이 같이 있으면
> 청크가 오염되고 RLS로 막을 방법이 없다.
> → **RAG는 문서 단위 티어로만 안전하다.** 그래서 비정형은 대부분 `analyst_only`로 수렴하고,
> `U`가 낮아지며 `R` 감점이 커진다. 모델의 편향이 아니라 실제 제약이다.

| 11 | **메일** *(구 Phase 3)* | 비정형 | 47 | RAG | 🆕 | |
| — | **메신저·미팅** *(구 Phase 4)* | — | **게이트 탈락** | — | | 원천 미확보(Jandi export 샘플 없음) |

> 4위·5위는 1점 차라 사실상 동급이고, 둘 다 원천이 `quarterlyupdate`라 **함께 착수하는 게 자연스럽다**.
> 초안에 있던 "테마·기술태깅" 항목은 5위 배치태깅에 흡수됐다.

양식별 평균: **정형 85 / 하이브리드 84 / 비정형 56.** 비정형이 낮은 건 데이터가 열등해서가 아니라 (a) 현재 수요가 정형 편중(84%)이고 (b) 문서 단위 티어라 권한 리스크가 크기 때문이다(§7.4).

#### 세 가지 결론

1. **상위 5개 중 4개가 신규 구축이 아니다** — 권한 개방 1, 확보문서 추가추출 1, 기존 필드 도구화 2. 인프라 비용 없이 수요 1·2위를 친다.
2. **§4 백로그(드라이브→메일→메신저)는 9·11위·탈락이다.** 원인은 명확하다 — 그 순서는 **소스 확보 난이도순**인데, 실측해보니 **난이도와 수요가 역상관**이었다.
3. **법인상태·법적사건이 숨은 공동 1위**다. 감액검토 STEP1(부도·휴업·청산·압류·회생)이 전부 여기이고, 원천은 **이미 확보한 등기부 PDF**다. 재무(Phase 1)로 STEP3만 커버한 상태를 완성시킨다.

### 7.7 RAG는 왜 보류인가 — 착수 조건

§0에서 "하이브리드(정형 도구 + RAG)"를 확정했고 방향은 유효하다. 다만 **RAG의 착수 시점**은 아래 근거로 뒤로 뺀다.

**(a) 지금도 RAG를 하고 있다 — 가장 비싼 형태로.** `scanPortfolio` full-scan은 retrieval 없이 174k 토큰(§7.1c)을 통째로 투입한다. 비싸고, 느리고, 재현성이 없고, 오탐(피처링)이 났다. 즉 문제는 "RAG 미도입"이 아니라 **검색 없는 전량 투입**이다.

**(b) 관측된 비정형 수요 전부가 사전 태깅으로 커버된다.**

| 실제 질문 | 필요한 것 | 배치 태깅으로 되나 |
|---|---|---|
| "일본에서 사업하는 회사?" | 해외진출국 태그 | ✅ |
| "피지컬AI + 서울 + 7년미만" | 기술테마 태그 | ✅ |
| "소프트랜더스와 비슷한 섹터 선배 포폴사" | 섹터(기존 필드) + 성숙도 태그 | ✅ |
| "상장한 기업들?" | **상장 확정 사실** | ❌ → 3위 항목(외부 공개정보)이 담당 |
| | 상장 *추진 단계·계획* | ✅ 보조 |

> ⚠️ **상장은 태깅으로 풀면 안 된다.** 본문 서술에서 상장을 뽑는 것이 바로 피처링 오탐
> (경쟁사 상장 언급을 자사 상장으로 집계)을 낳은 경로다. **확정 사실은 3위 항목(KRX 등 공개정보)이
> 권위 있는 원천**이고, 태깅은 "상장 추진 중" 같은 진행 단계만 보조한다. 둘은 중복이 아니라 역할 분담이다.

RAG의 고유 가치는 **예상 못 한 질문**에 답하는 것인데, 그 수요는 아직 실측 근거가 없다(단 §7.1d의 수요 억제 가능성은 남는다).

**(c) 유지보수 관점 — 검사 가능한 것 > 불투명한 것.**
배치 태깅의 산출물은 **테이블**이라 `/financial-status` 탭처럼 눈으로 훑어 틀린 걸 찾을 수 있다.
RAG의 산출물은 유사도 점수라, 답이 이상할 때 "검색이 잘못 물어온 건지 모델이 잘못 읽은 건지" 가리려면 임베딩 디버깅이 필요하다. **조용히 틀리지 않고, 틀리면 눈에 보이는** 설계를 우선한다.

> **RAG 착수 조건** — 아래 중 하나가 충족되면 재검토한다.
> ① 배치 태깅으로 안 잡히는 질문이 로그에 실제로 쌓인다 (§7.1d의 계측 장치 선행)
> ② 코퍼스가 드라이브·메일까지 확장돼 사전 태깅이 감당 불가해진다
>
> 참고로 기술적 난이도 자체는 낮다 — 이 코퍼스는 **평균 263자라 이미 청크 크기**여서
> RAG에서 가장 실패하기 쉬운 부분(문서 분할 전략)이 필요 없다. 보류 사유는 난이도가 아니라 **필요성과 유지보수성**이다.

### 7.8 재산출 방법

점수·가중치는 **파라미터**다. 항목이 늘거나 §7.1 실측이 갱신되면 표만 고치고 다시 돌린다.

```bash
node scripts/priority-score.mjs                # 순위표 + 양식별 평균
node scripts/priority-score.mjs --sensitivity  # 축별 스윕(0~8) + 극단 시나리오 9종
```

스크립트(`scripts/priority-score.mjs`)는 외부 의존이 없고, 축 정의·가중치·후보 점수가 상단 표에 모여 있다.
게이트 탈락 항목은 `gate` 필드로 사유를 적어 두면 점수 산출에서 빠지고 목록 하단에 사유와 함께 표시된다.

**재산출이 필요해지는 시점**
- §7.1d의 계측 장치(잔디 로깅 · tool 파트 저장)를 붙여 D·G를 실측으로 갱신할 때 — **가장 우선**
- 상위 항목을 착수해 `G(실패갭)`가 0으로 떨어질 때 (완료 항목은 목록에서 제거)
- 새 후보가 생기거나 원천 사정이 바뀔 때 (예: 드라이브 API 권한 확보 시 `S` 상승)
